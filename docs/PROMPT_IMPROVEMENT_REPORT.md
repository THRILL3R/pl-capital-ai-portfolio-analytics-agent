## Root causes (from the 6/10 run) and prompt changes

The prompt changes are general, schema-level conventions in `GeminiSQLGenerator`. They extend `FINANCIAL_SEMANTICS` and add a new `RESULT_CONVENTIONS` block. They contain no question IDs, official SQL, expected values or fund-specific outputs; `test_53` enforces this.

| Q | Why it failed | Convention added | After |
|---|---|---|---|
| Q5 | Returned 3 of 5 columns (no `holding_id`, `quantity`). | **Projection completeness:** holding-level rows include `holding_id`, `symbol`, `company_name`, `quantity` and the metric. Security rows include symbol and name; portfolio rows include the portfolio name. | PASS |
| Q6 | `GROUP BY` without `ORDER BY`. | **Deterministic ordering:** grouped aggregates are ordered by the computed metric `DESC`; top-N requests are ordered by the ranking metric with `LIMIT`. | PASS |
| Q7 | `LEFT JOIN` + `COALESCE` gave 13 rows (5 at 0%); total value was not returned; no order. | **Category share:** only portfolios that hold the category (inner join), unless the question asks for zero rows; the denominator is all holdings. **Percentages** also return the numerator and denominator. Ordering as above. | **FAIL**: columns, order and values are now correct, but the 5 zero-Technology portfolios are still included |
| Q8 | Returned only a sector count. | **Diversification convention:** `COUNT(DISTINCT sector_id)` over Stock holdings; total holdings including bonds; ratio `ROUND(CAST(sector_count AS REAL)/total_holdings, 3)`; no substitute metrics. | PASS |
| Q4 | Did not fail before; this regression was introduced by the first draft of the new rules. The live smoke test caught it: a total became a per-portfolio listing. | **Granularity first:** a total, count or average over a set is one aggregate row with no `GROUP BY`. This takes precedence over projection and ordering. | PASS |

## Remaining failure — Q7

Gemini returned exactly the 8 expected rows, in the expected order with matching values, followed by 5 extra rows with 0% Technology. The question says "for each portfolio", and the model weighted that above the scope rule. A stronger instruction could close the gap, but it would need another live run to verify. This was not done, to avoid spending further API credits without approval.

## Follow-up: targeted Q7 fix (separate result)

The category-exposure rule was rewritten in general terms. The result rows are only portfolios with at
least one qualifying holding. The rule forbids the construction that produced the zero rows (starting
from all portfolios and `LEFT JOIN`ing the category aggregate, or `COALESCE(..., 0)`). It states that
"for each / per / by / every portfolio" is not a request for zero rows, and lists explicit phrasings
that *do* allow zero-exposure rows. No sector, portfolio, question ID or expected value is named in
the rule; `test_59` enforces this.

|---|---:|---|
| `evaluate.py --use-llm --questions 7` ([report](EVALUATION_Q7_TARGETED.md)) | 1 | **Q7 PASS**: Gemini SQL, no fallback, inner join, 8 rows in official order |

This is a **subset result**. The latest complete live run remains **9/10**; a live 10/10 is not
claimed until a full `--use-llm` run is repeated with the current prompt. Gemini named two of its
columns `numerator` and `denominator`, following the projection rule's wording literally. Column
names are not scored, but this is cosmetic room for improvement.

New mocked tests: `test_59` (the rule is present and generic), `test_60` (by default only holders
